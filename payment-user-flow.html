User Flow - Sistema de Pagos

Visualización de flujos de usuario del sistema de gestión de pagos

Flujo 1: Pago Simple a un Proyecto

Proceso completo para registrar un pago a un único proyecto.

1

Usuario inicia acción

Click en Dropdown "Registrar Pago" → Opción "Pago a Proyecto"

📍 Ubicación: PaymentSummaryCard → Dropdown Button
2

PaymentToProjectDialog se abre

Modal con PaymentToProjectForm (flujo 1:1 simplificado)

Componente:

  • Dialog: PaymentToProjectDialog
  • Form: PaymentToProjectForm
  • Ubicación: components/dialogs/payments/
3

Usuario completa formulario

Ingresa datos del pago en PaymentToProjectForm

✓ Busca proyecto: #2024-001
✓ Monto: $300,000 (no excede balance)
✓ Fecha: Hoy
✓ Método: Transferencia
✓ Referencia: TRX-123456 (requerida)
📍 Validación: lib/validations/payment-validations.ts
4

Submit del formulario

POST /api/payments con payload validado

📍 API Route: app/api/payments/route.ts
POST /api/payments Body: { customerId: "abc-123", // ← Derivado del proyecto amount: 300000, currency: "CLP", // ← Derivado del proyecto date: "2024-11-05", paymentMethodId: "xyz-789", reference: "TRX-123456", allocations: [ { projectId: "2024-001", allocatedAmount: 300000 // ← 100% del monto } ] }
5

Validaciones API (14 checks: 6 frontend + 8 backend)

Sistema ejecuta validaciones automáticas

Frontend (Zod Schema) - 6 validaciones:

✅ 1. customerId: UUID válido
✅ 2. amount > 0, max 2 decimales
✅ 3. currency: 3 letras exactamente
✅ 4. date: fecha válida
✅ 5. paymentMethodId: UUID válido
✅ 6. allocations: min 1, no duplicados

Backend (Database) - 8 validaciones:

✅ 7. Customer existe en DB
✅ 8. PaymentMethod existe
✅ 9. Reference provisto si requerido
✅ 10. No projectIds duplicados
✅ 11. Todos los proyectos existen
✅ 12. Proyectos pertenecen al cliente
✅ 13. Proyectos tienen misma currency
✅ 14. Suma allocations = amount (±0.01)
6

✅ Success - Pago creado

Payment y PaymentAllocation creados en DB

Entidades creadas:

  • → Payment: $300,000 (status: ACTIVE)
  • → PaymentAllocation: $300,000 → Proyecto #2024-001
7

Toast + Refetch

Feedback al usuario y actualización de UI

🎉 Toast: "Pago registrado exitosamente"

onSuccess() ejecutado:

  • → PaymentSummaryCard refetch → Balance actualizado
  • → ProjectPaymentsTable refetch → Nuevo pago visible
📍 Componentes: components/summarys/ + components/tables/

🎯 Estado Final del Proyecto

Total Proyecto

$500,000

Total Pagado

$300,000

Balance Pendiente

$200,000

Flujo 2: Pago con FIFO Automático

Distribución automática de un pago entre múltiples proyectos usando algoritmo FIFO.

Contexto inicial:

Cliente tiene 3 proyectos pendientes ordenados por fecha (más antiguo primero):

#2024-001 (Jun) Balance: $300,000
#2024-002 (Ago) Balance: $400,000
#2024-003 (Oct) Balance: $300,000
1

Usuario inicia acción

Click en Dropdown "Registrar Pago" → Opción "Pago a Cliente"

PaymentToCustomerDialog se abre

  • Dialog: PaymentToCustomerDialog
  • Form: PaymentToCustomerForm
  • Tab default: "FIFO Automático"
2

Ingresa monto y método

✓ Monto: $500,000
✓ Método: Efectivo
3

Click "Calcular FIFO" (Tab FIFO Automático)

Sistema ejecuta algoritmo FIFO automáticamente

💡 Usuario está en tab "FIFO Automático" (default). Puede cambiar a tab "Distribución Manual" después.

calculateFIFO(500000, [ { id: '#2024-001', balance: 300000, date: 'Jun' }, { id: '#2024-002', balance: 400000, date: 'Ago' }, { id: '#2024-003', balance: 300000, date: 'Oct' } ])
4

Algoritmo FIFO ejecuta

Distribución automática por antigüedad

Step 1: Proyecto más antiguo (#2024-001)

→ Balance: $300,000

→ Remaining: $500,000

→ Asignar: $300,000 (cierra completo ✅)

→ Remaining after: $200,000

Step 2: Segundo proyecto (#2024-002)

→ Balance: $400,000

→ Remaining: $200,000

→ Asignar: $200,000 (abono parcial ⚠️)

→ Remaining after: $0

Step 3: Tercer proyecto (#2024-003)

→ Remaining: $0

→ Skip (sin fondos disponibles)

5

Tabla muestra allocations calculadas

Usuario puede editar manualmente si lo desea

Proyecto Balance Monto Asignado Estado
#2024-001 $300,000 $300,000 ✅ Completo
#2024-002 $400,000 $200,000 ⚠️ Parcial
Total Pago $500,000 ✅ OK
6

Submit → POST /api/payments

POST /api/payments Body: { customerId: "customer-1", amount: 500000, currency: "CLP", date: "2024-09-10", paymentMethodId: "efectivo-id", allocations: [ { projectId: "2024-001", allocatedAmount: 300000 }, { projectId: "2024-002", allocatedAmount: 200000 } ] }
7

✅ Success - 2 allocations creadas

Entidades creadas:

  • → Payment: $500,000 (status: ACTIVE)
  • → PaymentAllocation: $300,000 → #2024-001
  • → PaymentAllocation: $200,000 → #2024-002

🎯 Estado Final de Proyectos

#2024-001 Balance: $0 (Pagado completo ✅)
#2024-002 Balance: $200,000 (Pendiente)
#2024-003 Balance: $300,000 (Sin cambios)

Flujo 3: Anulación de Pago

Proceso de soft delete de un pago con auditoría completa.

Caso de uso:

Se detectó un pago duplicado que debe ser anulado. El sistema mantiene auditoría completa.

1

Usuario identifica error

En ProjectPaymentsTable encuentra pago incorrecto

Pago erróneo detectado:

  • → ID: payment-5
  • → Monto: $50,000
  • → Fecha: 25/Oct/2024
  • → Referencia: TRX-CANCEL123
  • → Status: ACTIVE
2

Click botón "Anular"

Solo visible si status === 'ACTIVE'

📍 Ubicación: ProjectPaymentsTable → Action Button
3

AlertDialog se abre

Confirmación con detalles del pago y textarea para razón

⚠️ ¿Anular este pago?

Esta acción no se puede deshacer.

Monto: $50,000

Método: Transferencia

Fecha: 25/Oct/2024

4

Usuario confirma anulación

Ingresa razón y click "Anular Pago"

📍 API Route: app/api/payments/[id]/cancel/route.ts
POST /api/payments/payment-5/cancel Body: { reason: "Error en transferencia - fondos devueltos" }
5

API ejecuta soft delete

UPDATE (no DELETE) - mantiene auditoría

UPDATE payment SET status = 'CANCELLED', cancelledAt = NOW(), cancelledReason = 'Error en transferencia - fondos devueltos' WHERE id = 'payment-5' -- ❗ NO se elimina PaymentAllocation -- calculateProjectBalance() ignorará este allocation

⚠️ Importante:

  • No hard delete - registro permanece en DB
  • PaymentAllocation NO se elimina
  • Auditoría completa mantenida
  • Cambio es irreversible (no hay "reactivar")
6

✅ Success - Toast + Refetch

🎉 Toast: "Pago anulado exitosamente"

Refetch payments ejecutado

7

UI actualiza automáticamente

Cambios visuales en tabla y balance

ProjectPaymentsTable:

  • → Badge cambia: Activo → Anulado
  • → Botón "Anular" desaparece
  • → Tooltip muestra cancelReason

PaymentSummaryCard:

  • → calculateProjectBalance() ejecuta
  • → Ignora allocation de pago CANCELLED
  • → Balance aumenta automáticamente

🔄 Comparación Antes/Después

Antes (con pago erróneo):

Total pagado:

$350,000

(200k + 100k + 50k)

Balance pendiente:

$50,000

Después (corregido):

Total pagado:

$300,000

(200k + 100k)

Balance pendiente:

$100,000 ✅

Flujo 4: Corrección Manual de Distribución

Usuario prefiere distribución diferente a la sugerida por FIFO.

Escenario:

FIFO sugiere una distribución, pero el usuario tiene preferencia estratégica diferente.

1

Usuario abre PaymentToCustomerDialog

Click en Dropdown "Registrar Pago" → "Pago a Cliente"

Ingresa datos básicos:

  • ✓ Selecciona cliente
  • ✓ Monto: $400,000
  • ✓ Fecha y método de pago
2

Click "Calcular FIFO"

Sistema genera sugerencia automática

FIFO sugiere:

#2024-001 $300,000
#2024-002 $100,000
3

❌ Usuario prefiere otra distribución

Cambia a tab "Distribución Manual" para editar montos

Razón del cambio:

"Quiero abonar más al proyecto #2024-002 porque es más urgente"

💡 En tab "Distribución Manual", puede editar cada monto manualmente (override de FIFO)

4

Edición manual de montos

Usuario modifica allocations directamente en tabla

Proyecto Balance Monto Asignado
#2024-001 $300,000
#2024-002 $400,000
5

Validación en tiempo real

Sistema verifica que suma = monto total

Total del pago: $400,000
Total asignado: $400,000
Diferencia: $0 ✅

💡 Si hubiera diferencia, mostraría error rojo y deshabilitaría Submit

6

Submit con distribución manual

POST /api/payments Body: { customerId: "customer-1", amount: 400000, currency: "CLP", date: "2024-11-05", paymentMethodId: "transferencia-id", reference: "TRX-MANUAL-123", allocations: [ { projectId: "2024-001", allocatedAmount: 150000 }, { projectId: "2024-002", allocatedAmount: 250000 } ] }
7

✅ Allocations creadas según preferencia

Sistema respeta distribución manual del usuario

Resultado:

  • → Pago registrado con distribución manual (no FIFO)
  • → Usuario tiene control total sobre asignación
  • → Sistema solo valida que suma sea correcta

🎯 Estado Final (Distribución Manual)

#2024-001

Balance original: $300,000

Abonado: $150,000

Pendiente: $150,000

#2024-002

Balance original: $400,000

Abonado: $250,000

Pendiente: $150,000

💡 Diferencia vs FIFO: Proyecto #2024-002 recibió más fondos según prioridad estratégica del usuario

Flujo 5: Pago en Cuotas sin Interés

Sistema de cuotas comercio que divide un pago en múltiples cuotas automáticas.

Contexto:

El cliente quiere realizar un pago de $300,000 pero dividido en 3 cuotas sin interés.

Monto total: $300,000
Número de cuotas: 3 cuotas
Método de pago: Tarjeta (con cuotas habilitadas)
1

Usuario inicia acción

Click en Dropdown "Registrar Pago" → Opción "Pago a Proyecto"

📍 Ubicación: PaymentSummaryCard → Dropdown Button
2

Seleccionar método de pago

Usuario selecciona método con cuotas habilitadas

Requisitos del método de pago:

  • → hasInstallments: true
  • → maxInstallments: 12 (hasta 12 cuotas permitidas)
  • → Ejemplo: Tarjeta de crédito, WebPay Plus
3

Seleccionar número de cuotas

Campo de cuotas aparece dinámicamente al elegir método con cuotas

✓ Proyecto: #2024-001
✓ Monto: $300,000
✓ Método: Tarjeta de Crédito
💳 Cuotas: 3 cuotas sin interés
4

Submit del formulario

POST /api/payments con selectedInstallments

POST /api/payments Body: { customerId: "abc-123", amount: 300000, currency: "CLP", date: "2024-11-05", paymentMethodId: "tarjeta-id", reference: "TRX-123456", selectedInstallments: 3, // ← NUEVO: Número de cuotas allocations: [ { projectId: "2024-001", allocatedAmount: 300000 } ] }
5

Sistema calcula cuotas automáticamente

Backend ejecuta algoritmo de división con remainder

// Algoritmo de cálculo de cuotas baseAmount = Math.floor((300000 / 3) * 100) / 100 = 100000.00 totalBase = 100000.00 * 2 = 200000.00 lastAmount = 300000 - 200000 = 100000.00 // ← Remainder Cuota 1: $100,000.00 - Vence: 2024-11-05 (día 0) Cuota 2: $100,000.00 - Vence: 2024-12-05 (día 30) Cuota 3: $100,000.00 - Vence: 2025-01-04 (día 60) ──────────── Total: $300,000.00 ✅

⚠️ Importante:

  • Primera cuota vence el día 0 (fecha de compra)
  • Cuotas siguientes cada 30 días
  • Última cuota absorbe remainder para suma exacta
  • Sin intereses (cuota = monto total / n)
6

✅ Success - Payment + Installments creados

Entidades creadas:

  • → Payment: $300,000 (status: ACTIVE, selectedInstallments: 3)
  • → PaymentAllocation: $300,000 → Proyecto #2024-001
  • → Installment #1: $100,000 (due: 2024-11-05, status: pending)
  • → Installment #2: $100,000 (due: 2024-12-05, status: pending)
  • → Installment #3: $100,000 (due: 2025-01-04, status: pending)
7

⏰ Cron Job marca cuotas como pagadas

Vercel Cron Job ejecuta diariamente a medianoche

POST /api/cron/mark-installments-paid Authorization: Bearer {CRON_SECRET} // Busca cuotas pendientes vencidas WHERE status = 'pending' AND dueDate <= TODAY // Batch update UPDATE installment SET status = 'paid', paidDate = NOW() WHERE id IN (...)

📅 Timeline automático:

  • → 2024-11-05: Cuota 1 marcada como "paid" (día 0)
  • → 2024-12-05: Cuota 2 marcada como "paid" (día 30)
  • → 2025-01-04: Cuota 3 marcada como "paid" (día 60)

🎯 Vista de Cuotas en Sistema

# Monto Vencimiento Pagada Estado
1/3 $100,000 05/Nov/2024 05/Nov/2024 ✅ Pagada
2/3 $100,000 05/Dic/2024 - ⏳ Pendiente
3/3 $100,000 04/Ene/2025 - ⏳ Pendiente

💡 Nota: El sistema marca automáticamente las cuotas como pagadas cuando llega su fecha de vencimiento. No requiere acción manual.
